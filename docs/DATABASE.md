# Database

Postgres, in a private schema called `app`. The schema is in [apps/api/migrations](../apps/api/migrations): `001_init.sql`, `002_accounts.sql` and `003_devices_and_reauth.sql`. The planned host is Supabase, used as plain Postgres. It has not run there yet: tests and local development use `embedded-postgres`.

Column types below are from the migration. "Sealed" means AES-256-GCM encrypted by the application with the user's data key, before it reaches the database. See [encryption](modules/encryption.md).

### `app.otp_codes`

| Column | Type | Null | Encryption | Notes |
| --- | --- | --- | --- | --- |
| `id` | uuid, primary key | No | Plain | Default `gen_random_uuid()` |

### `app.otp_failures`

One row per wrong guess at a live code, for the daily caps. `login`, `register` and `password_reset` count together: 20 a day per address and 5 per address and client from unknown devices, or 20 a day per known device. Signed-in purposes: 20 a day per address and purpose, with both new columns null.

| Column | Type | Null | Encryption | Notes |
| --- | --- | --- | --- | --- |
| `id` | uuid, primary key | No | Plain | |
| `quota_hash` | bytea | No | HMAC | As above |
| `purpose` | text | No | Plain | No `CHECK` here |
| `source_hash` | bytea | Yes | HMAC | Key `OTP_PEPPER`, domain `otp-failure-source:`, of `quota_hash` and the client key. Sign-in purposes from an unknown device. From `003` |
| `device_id` | uuid | Yes | Plain | References `device_tokens`, cascade delete. Sign-in purposes from a known device. At most one of the two is set. From `003` |

### `app.login_failures`

One row per failed password attempt, for the caps: from an unknown device, 10 a day per address and client and 100 a day per address; from a known device, 10 an hour for that device. Also counts addresses with no account, so it says nothing about who has one. A row is written before the hash runs, and removed if the password was right. From `002_accounts.sql`, reworked in `003_devices_and_reauth.sql`.

| Column | Type | Null | Encryption | Notes |
| --- | --- | --- | --- | --- |
| `id` | uuid, primary key | No | Plain | |
| `quota_hash` | bytea | No | HMAC | Key `EMAIL_INDEX_KEY`, of the canonical address, in its own domain (`login-quota:`), so it can't be joined with `otp_codes.quota_hash` |
| `source_hash` | bytea | Yes | HMAC | Key `OTP_PEPPER`, domain `login-failure-source:`, of `quota_hash` and the client key. Set for an unknown device |
| `device_id` | uuid | Yes | Plain | References `device_tokens`, cascade delete. Set for a known device. `CHECK` that exactly one of the two is set |
| `created_at` | timestamptz(3) | No | Plain | Purged after 24 hours |

### What a database reader can see

Plaintext: ids, timestamps (when a person checked in, wrote, signed in), row counts, the journal's 4 KB size step, consent versions, the audit action and day. Not visible: email, name, device, answers, score, severity, or journal text.

`assessments.payload` always has the same ciphertext size, so a dump cannot tell severities apart by length. This is tested in [hardening.test.ts](../apps/api/test/hardening.test.ts).

## Setting up and checking a database

`npm run db:setup` creates or updates the runtime role, sets its password as a SCRAM verifier so the plain password never reaches the server, runs migrations and verifies. `npm run db:verify` is the read-only report. Both read `.env.setup`. They have only met embedded Postgres. See [DEPLOYMENT.md](DEPLOYMENT.md).

## Roles and grants

| Role | Used by | Purpose |
| --- | --- | --- |
| Migration role, via `DATABASE_MIGRATION_URL` | `npm run migrate` only | Creates the schema and tables, so it owns them. On Supabase this is `postgres`. |
| `anxiocare_runtime`, via `DATABASE_URL` | The server, `purge`, `rotate-keys` | Least privilege. |

Role attributes, from `runtimeRoleSql` in [apps/api/src/db.ts](../apps/api/src/db.ts): `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS NOINHERIT CONNECTION LIMIT 40`. `npm run generate-secrets -w @anxiocare/api` prints this SQL with a new password. If the role does not exist when migrations run, the migration creates it with `NOLOGIN`, so that the grants are valid.

The role can write audit rows but cannot read them back. It can delete them because the retention purge runs as this role.

**Boot check.** `assertRuntimeRole` stops the server if the connected role is a superuser, can create roles or databases, can bypass RLS, or owns any table in `app`. In production, config also refuses a `DATABASE_URL` user of `postgres` or `supabase_admin`, or one identical to the migration URL.

## Row-level security

RLS is enabled on all twelve tables. Eleven have one policy:

```sql
CREATE POLICY runtime_all ON app.<table> TO anxiocare_runtime USING (true) WITH CHECK (true);
```

`schema_migrations` has none. The effect, in plain terms:

- `anxiocare_runtime` can reach every row its table grants allow.
- Any other non-owner role, such as Supabase's `anon` or `authenticated`, sees nothing, even if someone grants it a table by mistake.
- **RLS does not separate one person from another.** `USING (true)` lets the runtime role see all users' rows. That separation comes only from `WHERE user_id = ...` in each query, and is covered by the cross-user tests in [data.test.ts](../apps/api/test/data.test.ts).
- The migration role owns the tables, and RLS is not forced, so it can see every row.

Why it is this way: [decision 005](decisions/005-rls-role-scoped-policies.md). The design spec says "RLS enabled with no policies". The code is what applies.

## Connections

- [`databaseOptions`](../apps/api/src/db.ts): `prepare: false`, because the Supavisor pooler does not keep named prepared statements usable across clients.
- Use the Supavisor **session** pooler. Transaction mode is not supported. Neither has been tried against a real pooler yet.
- TLS verify-full: `DATABASE_CA_CERT` is pinned, and it is mandatory in production. Without it, as in local development, TLS is off.
- Each instance holds up to `DATABASE_POOL_MAX` connections, default 5.

## Migrations

Runner: [apps/api/src/migrate.ts](../apps/api/src/migrate.ts). `npm run migrate` needs only `DATABASE_MIGRATION_URL`, plus `DATABASE_CA_CERT` in production. It does not need the encryption keys. `npm run dev:api` also runs it, as the local superuser.

- Files match `^\d{3}_[a-z0-9_]+\.sql$`. Any other name is silently ignored.
- Everything pending runs in one transaction, under an advisory lock, so two deploys cannot race and a failure rolls back all of it. `CREATE INDEX CONCURRENTLY` cannot be used.
- An applied file whose checksum changed, or that is missing from disk, stops the run. History must not be rewritten.
- The server does not migrate at boot. `render.yaml` runs it as `preDeployCommand`, and starts the server without the migration URL.

Applied so far: `001_init.sql`, `002_accounts.sql`.

### Adding a migration

1. Create `apps/api/migrations/NNN_short_name.sql`, the next number, in lower case. Never edit an applied file. Locally, editing `001` gives a checksum error until you run `DEV_FRESH=1 npm run dev:api`.
2. New tables go in `app`, never `public`.
3. For a new table, do all of these in the same file:
   - `ALTER TABLE app.x ENABLE ROW LEVEL SECURITY;`
   - `GRANT` only what the runtime role needs.
   - `CREATE POLICY runtime_all ON app.x TO anxiocare_runtime USING (true) WITH CHECK (true);`
   - Foreign key to `users` with `ON DELETE CASCADE` if it holds a person's data. If it does not cascade, add it to the erasure and purge code.
4. Sensitive values go in a `_ct` bytea column sealed by `sealText` or `sealJson`, with a new `PAD_STEP` entry in [crypto.ts](../apps/api/src/crypto.ts). Only ids, timestamps, hashes, counters and labels may be plain.
5. Update the tests that pin the schema on purpose:
   - `RUNTIME_GRANTS` in [db-checks.ts](../apps/api/src/db-checks.ts), or `db:verify` will report the grant as extra
   - `public holds none of our tables; app holds all of them` in [database.test.ts](../apps/api/test/database.test.ts)
   - `plaintext columns are limited to ids, timestamps, hashes and labels` and `a raw SELECT of every table shows no plaintext` in [encryption.test.ts](../apps/api/test/encryption.test.ts)
   - `hard-deletes every row, leaving only pseudonymous audit rows` in [erasure.test.ts](../apps/api/test/erasure.test.ts)
6. Add a person's new data to `GET /me/export`.
7. Keep it backward compatible: the old server keeps running while the pre-deploy step applies the migration.
8. Update this file.

`npm test -w @anxiocare/api` applies all migrations to a real Postgres.
